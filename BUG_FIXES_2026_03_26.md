# Critical Bug Fixes - 2026-03-26

## Summary
Fixed three critical bugs that caused trades to execute successfully in Alpaca (paper trading) but NOT be saved to the SQLite database, resulting in data loss and stale cooling period calculations.

## Bug #1: Missing Exception Handling in Trade Opening (CRITICAL)

**Location:** `agent/trader.py`, line 192 in `execute_signal()` method

**Root Cause:**
- When `self.memory.save_trade(trade_data)` was called, there was NO try/except wrapper
- If the database operation failed for ANY reason (lock timeout, disk full, schema mismatch, etc.), the exception would propagate uncaught
- However, the Alpaca order had ALREADY been submitted (line 165) BEFORE the DB save
- Result: Trade executed in Alpaca but not saved to DB, creating orphaned positions

**Evidence:**
- From user notes: Coach report showed 10 trades executed in Alpaca on 23/03 (SBUX SHORT +$144, OXY SHORT +$63, 4x PFE shorts losing, etc.)
- But these trades were NOT in the database, causing stale data issues
- The cooling period calculation read an empty trade history and would fail

**Fix:**
Wrapped the entire trade save and notification block in try/except:
```python
try:
    trade_id = self.memory.save_trade(trade_data)
    # ... rest of processing ...
    return {"status": "executed", "trade": trade_data, ...}
except Exception as e:
    logger.error(
        f"CRITICAL: Trade executed in Alpaca (order #{order.get('id')}) "
        f"but FAILED to save to database: {e}",
        exc_info=True
    )
    return self._blocked(signal, f"CRITICAL: Order submitted to Alpaca but DB save failed: {e}", "db_save_failure")
```

This ensures:
1. The error is logged prominently with full stack trace
2. The failure is explicitly tracked in the return value
3. The caller (core.py) knows the trade was placed but not recorded

## Bug #2: Poor Exception Handling in Trade Closing

**Location:** `agent/trader.py`, lines 414-463 in `close_position()` method

**Root Cause:**
- The broad `except Exception as e` at line 462 caught BOTH Alpaca errors AND database errors
- If `self.memory.close_trade()` at line 430 failed with a database error, it would be caught silently
- The Alpaca close order had already been submitted, but the DB update was skipped
- Result: Position closed in Alpaca but marked as "open" in database, causing reconciliation issues

**Fix:**
Separated database errors from broker errors with explicit handling:
```python
try:
    self.memory.close_trade(...)
except Exception as db_error:
    logger.error(
        f"CRITICAL: Trade closed in Alpaca (order #{order.id}) "
        f"for {symbol} but FAILED to update database: {db_error}",
        exc_info=True
    )
    raise  # Re-raise so caller knows about the DB failure
```

This ensures database failures are treated as critical errors and properly tracked.

## Bug #3: Consecutive Losses Counter - Counting All-Time Instead of Today (CRITICAL)

**Location:** `agent/memory.py`, lines 444-463 in `get_consecutive_losses()` method

**Root Cause:**
- The function queried: `WHERE status = 'closed'` WITHOUT filtering by date
- This counted ALL consecutive losses from the entire trading history, not just today
- On 23/03, if there were historical losses in the DB, the counter would immediately trigger cooling period
- Result: Agent was put on cooling period based on stale historical data, not today's performance
- This explains the log entry: "6 consecutive losses! Cooling for 30 minutes" at 17:17:06 even though no trades were actually in today's database

**Evidence:**
From agent_2026-03-23.log at 17:17:06:
```
[WARNING] agent.risk_manager (risk_manager.py:88): RISK BLOCKED: VWAP_Mean_Reversion BUY OXY - 6 consecutive losses! Cooling for 30 minutes
```

But earlier logs show no trades were saved to the database. The 6 consecutive losses counter was reading historical data.

**Fix:**
Changed the query to filter for today's trades only:
```python
def get_consecutive_losses(self) -> int:
    """Get number of consecutive losses today (most recent trades first)."""
    conn = self._get_conn()
    try:
        today_str = date.today().isoformat()
        rows = conn.execute(
            """SELECT pnl FROM trades
               WHERE status = 'closed'
                 AND timestamp LIKE ?
               ORDER BY exit_timestamp DESC LIMIT 10""",
            (f"{today_str}%",)
        ).fetchall()

```

This ensures only TODAY's closed trades are counted for the cooling period calculation.

## Bug #4: Missing Database Lock Timeouts

**Location:** `agent/memory.py`, line 35-41 in `_get_conn()` method

**Root Cause:**
- SQLite connections had no timeout configured
- WAL (Write-Ahead Log) mode is enabled, which can create lock contention
- If one process was writing, another process trying to read/write would hang indefinitely or fail with locked database errors
- Result: Intermittent failures to save trades, especially under load

**Fix:**
Added timeout settings to all database connections:
```python
def _get_conn(self) -> sqlite3.Connection:
    """Get a database connection with row factory."""
    conn = sqlite3.connect(str(self.db_path), timeout=10.0)  # 10 second timeout for locks
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA foreign_keys=ON")
    conn.execute("PRAGMA busy_timeout=10000")  # 10 second timeout in milliseconds
    return conn
```

This ensures:
1. Connections wait up to 10 seconds for write locks to be released
2. Operations fail gracefully if a lock cannot be acquired, rather than hanging
3. Errors are raised and logged properly instead of silently timing out

## Impact

These fixes ensure:

1. **Data Integrity:** All trades executed in Alpaca are now saved to the database, or the failure is explicitly logged as CRITICAL
2. **Accurate Cooling Period:** The cooling period only counts today's consecutive losses, not historical data
3. **Better Error Visibility:** Database failures are now prominent in logs with full stack traces, making debugging easier
4. **Concurrency Safety:** Database connections have proper timeout handling to avoid deadlocks and lock contentions
